# 灵枢协同办公套件 · 技术设计文档（v1.0 · 可执行版）

| 项目 | 内容 |
|---|---|
| 文档性质 | 可执行设计文档，面向 AI 辅助编码与人工架构管控 |
| 硬约束 | 小团队（有效人力 ≤ 5 人）；代码主体由 AI 生成；2 万总用户；**单文档 200 人并发协同** |
| 核心原则 | 在“单文档 200 并发”这条红线上，不做任何乐观假设；每条设计选择标注**验证方式**与**降级路径** |

---

## 一、约束驱动的核心取舍（先定调，再展开）

200 人单文档协同，是这份文档所有设计选择的**第一驱动力**。公开工程实践给出的参照系是明确的：

Yjs 单文档在约 **100 个并发编辑器**以内是舒适区，超出后 **awareness（光标/选区/presence）更新流量**会成为首要瓶颈。Univer 的官方宣称是“200 人同时编辑、1000 人同时查看”，但那是其**协同服务端（OT 路径）**的能力，灵枢使用的是 Univer OSS 内核 + 自建 Yjs 协同层，不能直接把 200 这个数字平移过来。

因此，200 人单文档的目标，不能靠“把 Yjs 原样接上去”达成。必须做三件事，缺一不可：

1. **awareness 与 content 的彻底分离与节流**：200 人场景下，光标流量远大于编辑流量，必须把 awareness 降级为“按需、限频、视口过滤”的轻量通道。
2. **写者与观者的权限分离**：不是所有 200 人都在“编辑”。设计上区分 **active editor（有写权限且正在输入）** 与 **spectator（只读或浏览）**，spectator 不产生 update 广播，只接收收敛后的状态。
3. **单文档内的负载不落在同一个协同网关进程上**：Hocuspocus 的 Redis 扩展会向**所有实例广播所有消息**，官方明确说“如果目的是降低 CPU 负载，不应该用 Redis 把所有实例连起来”。正确的做法是**按文档标识做一致性哈希路由**，让同一文档的 200 个连接落在同一个协同网关分片上，而不是让 200 人的广播流量穿透整个集群。

## 二、数据模型与分片策略

### 2.1 表格（筹）：sheet 级 Y.Doc 分片，不做单 Doc 承载整本工作簿

一本工作簿如果所有 sheet 共享一个 Y.Doc，200 人并发下的 Y.Doc 体积和 awareness 作用域都会失控。设计为：

- **Workbook 元数据 Doc**：一个轻量 Y.Doc，承载 sheet 列表、名称、顺序、权限等结构信息，所有 200 人同步这一个 Doc，但它的更新频率极低。
- **每个 Sheet 一个独立 Y.Doc**：sheet 内的单元格数据、公式、格式各自独立。200 人如果分散在多个 sheet，实际单 Doc 的并发压力远小于 200。
- **跨 sheet 公式引用**：一期只支持“引用已缓存的计算结果”，不做跨 sheet 的实时公式依赖图同步。跨 sheet 引用变更时，依赖 sheet 通过一次元数据 Doc 上的版本标记触发重算。这个取舍写入验收标准，避免陷入“跨 sheet 公式实时一致性”的无底洞。

> **验证方式**：M0 中跑“2 人同时编辑 sheet A + 2 人同时编辑 sheet B + 1 人在 sheet C 查看跨 sheet 公式结果”，确认 sheet 间无 update 泄漏，公式结果在元数据版本标记变更后正确刷新。

### 2.2 文档（笺）：逻辑分章锚点，一期不做真分片

TipTap/ProseMirror 的协同绑定是成熟的，但大文档的**初始 parse 成本**是真实瓶颈：ProseMirror 作者确认虚拟渲染并不能消除首次 parse 的开销。200 人同时打开一篇长文档时，parse 成本会乘以 200，形成服务端和客户端的同步压力。

一期策略：**限制单文档体量，预留分章锚点**。

- 单文档字数上限设为 **8 万字**（约 300–500 个 block 级别节点）。超过上限时引导用户拆分为多篇，产品层面接受这个约束。
- 在 ProseMirror schema 中，把 **top-level node 的边界**定义为“逻辑章节”，为二期按章节分片 Y.Doc 预留锚点。一期不实现分片加载，但 schema 注释和路由层不写死“一文档一 Y.Doc”。
- 如果 M1 实测发现 8 万字文档在 200 人打开场景下客户端 parse 超过 3 秒，二期将“文档分章分片”升级为必做项，而非可选。

## 三、协同层：Hocuspocus 的“分片路由 + awareness 治理”

### 3.1 部署拓扑：文档一致性哈希，而非 Redis 全联

不使用“所有 Hocuspocus 实例通过 Redis 互联”的对称拓扑。采用**一致性哈希网关**：

```text
客户端 → 负载均衡（按 document_id 做一致性哈希）→ Hocuspocus 分片实例
                                                      ↓
                                              仅该分片内的连接广播
                                                      ↓
                                            PostgreSQL（快照/op 流）
```

同一文档的 200 个 WebSocket 连接被路由到**同一个 Hocuspocus 实例或同一组亲和实例**。这样：

- 200 人的 update 广播**不会穿透到其他分片**，CPU 负载分散是有效的；
- Redis 只用于 **presence 的跨分片可见性**（如果一期不做跨分片 presence，Redis 可以完全不进入协同热路径）；
- 单分片容量规划：按 Hocuspocus 在低配资源下可维持数千连接的经验，一个分片承载 200 人单文档是充裕的，剩余容量用于同分片上的其他小文档。

**风险与对策**：一致性哈希意味着“一个爆款文档”会集中打到一个分片。这是可接受的——200 人是已知上限，不是无限弹性。如果未来出现单文档超过 200 人的需求，触发重新评估，而不是在一期为此设计复杂的动态再平衡。

### 3.2 Awareness 治理（200 人场景的核心工程）

默认的 Yjs awareness 行为在 200 人下不可用。实施四层治理：

| 层级 | 措施 | 参数/规则 |
|---|---|---|
| **频率** | 光标更新节流 | 客户端侧最高 20–30 次/秒，服务端侧 `awarenessThrottle` 合并广播 |
| **范围** | 视口过滤 | 只广播和渲染**当前可视区域**内的光标；视口外的光标在滚动进入时按需拉取一次位置快照 |
| **粒度** | 角色分层 | active editor 广播完整 awareness；spectator 只广播“在线状态”，不广播光标坐标 |
| **批次** | 服务端合并 | 开启 Hocuspocus 的 batching 能力，将 awareness 更新按 client id 去重合并后单帧下发 |

> **验证方式**：M0 中模拟 200 个虚拟客户端连接同一文档，其中 50 个持续移动光标。测量服务端 CPU、出站带宽、客户端帧率。基线：服务端单核 CPU 低于 70%，客户端编辑区域帧率不低于 30fps。不达标则优先降级为“只广播最近活跃的 20 个光标”，并在产品层面显示“N 人在线，M 人正在编辑”。

### 3.3 持久化：快照 + op 流，但接受“回滚精度分级”

- 每 **30 秒**或每 **500 个 update** 落一次 Yjs 快照到 PostgreSQL（JSONB 存储二进制编码）。
- op 流 append 到同一数据库的独立表，保留 **7 天**用于近期回滚。
- **版本历史的精度分级**：7 天内的任意点回滚基于 op 流，精度为“结构级 + 内容级”；超过 7 天的版本只保留**快照级回滚**（回到快照时刻的结构和内容状态）。在 UI 中明确标注回滚精度，而不是承诺“逐字符回滚任意历史”。

> 这个取舍直接服务于小团队的存储成本控制。Yjs 在关闭 GC 时内存和存储增长是真实压力，7 天 op 流窗口是在“可接受的回滚能力”和“不无限膨胀的存储”之间的明确边界。

## 四、后端与存储：单栈 Node.js，但把“不可逆决策”集中在一处

后端保持 **Node.js + Hono + PostgreSQL + Redis + MinIO** 的单栈，这是小团队 + AI 编码场景下综合维护成本最低的选择。但有一个决策需要单独说明：

**为什么不把协同网关换成 Go 或 Rust？** Hocuspocus 的 Node.js 实现在单分片 200 人场景下不是瓶颈——瓶颈在 awareness 流量和客户端渲染，而不在 Node 运行时本身。换语言的收益在这一期不成立，但引入的运维复杂度和 AI 生成代码的审查成本会显著上升。如果二期单分片连接数逼近 2000 以上，再评估 Hocuspocus 的 Rust 等价实现（如 hocuspocu-rs 这类镜像实现）作为可选路径。

**AI 生成代码的架构管控点**：后端中 AI 最可能生成“看似正确但违反设计约束”的代码的位置是**权限校验中间件**和**持久化扩展**。这两处不交给 AI 自由发挥：权限钩子（Hocuspocus 的 `onAuthenticate` / `onLoadDocument`）和快照落盘逻辑，由人工定义接口契约和测试用例，AI 只填充实现。其余 CRUD 和导入导出外围代码可以较大比例交给 AI，但必须有基于设计文档验收标准的集成测试兜底。

## 五、前端渲染策略：两条路径，两种降级

| | 表格（Univer OSS Canvas） | 文档（TipTap DOM） |
|---|---|---|
| **200 人下的大头** | Canvas 渲染本身是隔离的，风险在**选区/光标浮层**的 DOM 叠加 | ProseMirror 的 DOM 节点数量和 decoration 渲染 |
| **措施** | 只渲染可视区单元格；光标和选区以有限数量的浮层叠加，超出阈值时折叠为“+N 个光标”聚合标记 | 单文档 8 万字上限；协同光标只对可视区内的 active editor 渲染；spectator 不渲染远端光标 |
| **降级** | 如果 200 人下 Canvas 帧率不达标，切换到“协作只读模式”或“跟随模式”（仅显示当前发言者视口） | 如果 parse 时间超标，触发“精简视图”（折叠格式 decoration，只保留纯文本 + 基础块结构） |

**Univer 协同 bridge 的选择**：M0 必须验证 `@8space-lab/univer-collab-bridge`（clean-room 实现，基于公开 Univer OSS API 序列化 mutation 并通过 command service 回放）是否满足跨 sheet 协同的稳定性。如果 bridge 在 M0 中出现 update 丢失或公式重算不一致，降级路径是 **表格一期只做“单 sheet 实时协同 + 跨 sheet 手动刷新”**，而不是硬扛全 workbook 协同。

## 六、部署与运维：小团队的“可承受故障模式”

### 6.1 拓扑（最小可用生产）

```text
                    ┌─────────────────────┐
                    │   Nginx / LB         │
                    │  一致性哈希 by doc_id │
                    └──────┬──────────────┘
                           │
              ┌────────────┴────────────┐
              ▼                          ▼
     Hocuspocus 分片 A            Hocuspocus 分片 B
     （无 Redis 互联）             （无 Redis 互联）
              │                          │
              └────────────┬────────────┘
                           ▼
                 Hono API 服务（2 副本）
                           │
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
     PostgreSQL 16      Redis（仅 API 层     MinIO
     （主 + 只读从）     缓存/presence 非热路径）
```

- **协同网关无 Redis 互联**：规避“所有消息在所有实例上处理”的放大效应。
- **PostgreSQL 主从**：协同快照写入走主库，文档列表/搜索/元数据读取走从库。2 万用户规模下单主库足够，主从分离是为了给快照写入留出余量，而不是为了吞吐。
- **Redis 不进入协同热路径**：Redis 用于 API 层会话缓存和 presence 的跨分片可见性（如果二期需要），不用于 update 广播。这意味着 Redis 故障不会直接中断正在进行的协同编辑。

### 6.2 明确的故障模式与预期

| 故障 | 影响 | 团队预期 |
|---|---|---|
| 单个 Hocuspocus 分片崩溃 | 该分片上的文档协同中断，客户端自动重连到新分片并拉取最新快照 | 可接受：200 人单文档场景下，30 秒内重连并恢复是验收基线 |
| PostgreSQL 主库故障 | 快照落盘暂停，协同编辑继续（op 在内存和 op 流缓冲中），恢复后补写 | 可接受：不因为存储故障打断实时协同 |
| Redis 故障 | API 层缓存失效，presence 跨分片不可见，协同编辑不受影响 | 可接受：降级而非中断 |
| 单文档 200 人超出预期 | 该分片 CPU 升高，该文档的新连接被限流排队 | 可接受：明确上限，不做无限弹性 |

## 九、M0 红线验证实测结果（2026-10-31）

验证环境：本地 2 个协同分片（`ws://localhost:1234` / `ws://localhost:1235`）、PostgreSQL 16 + Redis、Hocuspocus 4.8.0、Univer 1.3.0、Edge headless（复用本机浏览器，不额外下载）。三项验证门全部通过。

### 9.1 门 ①：200 并发 + 编辑区帧率

压测口径：50 editor + 150 spectator 连接同一文档 30 秒，awareness 20Hz；内容更新延迟测 199 个接收端；帧率在真实浏览器中采样。

| 指标 | 实测 | 基线 |
|---|---|---|
| 服务端出站带宽 | 7.16 MB/s（234,402 条消息，约 0.9 KB/条） | 4–8 MB/s |
| 服务端 CPU | avg 42.0% / p95 57.3% / max 61.9% | 单核 < 70% |
| 内容更新延迟 | p50 39ms / p95 50ms | p95 < 500ms |
| awareness 状态数（两端视角） | 200 / 200 | = 200 |
| 观察者视角可见光标数 | 恰 20 | ≤ 20 |
| 编辑区帧率 | 6401 帧 / 20s，平均 320fps，帧间隔 p95 3.2ms，低于 30fps 的帧 0/6401 | ≥ 30fps |

> 口径说明：headless 环境下 `requestAnimationFrame` 不受 vsync 限制（实测可达 320fps），因此帧率结论应读作“主线程零卡顿”，而非渲染管线吞吐。真实设备的 30fps 验收仍需在 M1 用带窗口的浏览器复测。

关键工程结论：默认 awareness 无增量编码——每次 `setLocalStateField('cursor')` 都会下发该 client 的整份 state，这是 200 人带宽爆炸的根因。治理手段是“服务端按 clientId 剥离无槽位客户端的光标状态 + 20 秒级 TTL 定期放行刷新”，实测带宽从 38.8 MB/s 降到 7.16 MB/s，且光标不再完全丢失。

复跑：`pnpm loadtest:m0`、`pnpm fps:m0`

### 9.2 门 ②：Univer 跨 sheet 协同桥

验证口径：两个独立浏览器客户端（各自独立 Y.Doc）加入同一 workbook，交替在 3 个 sheet 上共写 20 个单元格，双向读回比对。

| 指标 | 实测 |
|---|---|
| op 流条数 | A=20 / B=20 |
| A / B 端一致率 | 20/20、20/20 |
| 两端最终值 | 一致 |

结论：`@8space-lab/univer-collab-bridge@0.2.2` 在 Univer 1.3.0 上满足跨 sheet 协同，**无需触发“单 sheet + 手动刷新”降级路径**。

两个必须固化的接入约束：

1. 桥插件 `static type = UNIVER_SHEET`，注册顺序必须是「先 `createWorkbook`，再 `registerPlugin`」，否则插件不会被 flush；
2. 插件在 `onSteady` 才注册服务并挂上 mutation 监听，**任何驱动 Univer 命令的自动化都必须等待服务注册完成**，否则本地 mutation 全部落空、op 流为 0（本次首轮失败即此原因）。

复跑：`pnpm bridge:m0 -- --writes 20`

### 9.3 门 ③：一致性哈希路由 / 不跨分片广播

验证口径：创建 24 篇文档确认路由分布；对每个分片各取一篇文档，同时建立「所属分片写入者 + 同分片读者 + 异分片观察者」，写入后检查广播、内容与 awareness 是否越界。

| 指标 | 实测 |
|---|---|
| 同一文档重复查询分片 | 恒定 |
| 文档分布 | 1234=11 / 1235=13 |
| 同分片读者收到更新 | 47ms |
| 异分片观察者收到消息 | 0 条 |
| 异分片内容 / awareness | 无 / 无 |
| 总判定 | 10/10 PASS |

附带修正：FNV-1a 对“仅末尾字符不同”的分片名（如 `...:1234` / `...:1235`）雪崩不足，64 个虚拟节点时环上弧长实测 88.2% : 11.8%，分配严重偏斜。已将 `pickShard` 默认 `virtualNodes` 提升至 **1024**，弧长收敛到 49.1% : 50.9%，2000 个 UUID 形态 key 实测 1015 : 985。

复跑：`pnpm routing:m0 -- --docs 24`

### 9.4 结论

M0 三项红线全部通过，M1 可按计划推进；M1 不得裁剪 200 人验证门。遗留待办：M1 起需要验证“出站带宽随 spectator 数量亚线性增长”，以及真实设备（带 vsync）下的 30fps 帧率。

### 9.5 M1 四项性能验收实测结果（2026-10-31）

验证环境同上（本地双分片、PostgreSQL 16 + Redis、Hocuspocus 4.8.0、Univer 1.3.0）。浏览器为本机 Edge（独占显示器，2560×1440 @ 319Hz）。四条门全部通过，复跑命令：`pnpm accept:m1 -- --gate sheet|doc|fps|bandwidth`。

**门 ①：表格单 sheet 200 人协同**

口径：headful Edge（窗口在前台，显示器 319Hz vsync），浏览器自身 1 条连接 + 压测端 49 editor + 150 spectator = 200；一边每秒输入一次，一边采样 `requestAnimationFrame` 间隔 20 秒。

| 指标 | 实测 | 基线 |

| 采样帧数 | 6,397 | — |
| 平均帧率 | 319.8 fps（受 319Hz 刷新率封顶） | ≥ 30fps |
| 帧间隔 p95 | 3.2ms | — |
| 最差 1 帧 | 106.4 fps | — |
| 低于 30fps 的帧 | 0 / 6,397 | 0 |

> 口径说明：M0 的 320fps 结论曾被标注为“headless 不受 vsync 限制”。本次在本机 319Hz 显示器上以 headful 复测，帧率恰好封顶在 319.8fps，可确认是真实 vsync 上限；压测端注入的是合成光标坐标（不是合法的 Yjs relative position），编辑器渲染这批远端光标时会抛出 `Unexpected case`，属于压测数据构造问题，真实客户端发送的是编码后的相对位置，不会触发；该异常只让测试条件更苛刻，不影响 0 慢帧结论。

口径：固定 50 个 editor，spectator 分别取 50 / 100 / 150，awareness 20Hz，预热 5s 后统计 20s 内全部客户端接收字节数。

### 9.6 M2 版本历史实现与验收（2026-10-31）

**存储与精度**：每次快照落盘除更新 `doc_snapshots` 当前态外，追加一条 `doc_snapshot_versions` 历史版本（版本号与落盘序号一致）。裁剪策略直接对应 §3.3 的精度分级：7 天内保留全部版本，7–90 天只保留每天最早一条，90 天以上与超过 7 天的 op 流一并清理。API 按时间判断精度：7 天内标“内容级”，超出标“快照级”，UI 不再承诺窗口外的逐字回滚。

**接口**：`GET /api/docs/:id/versions` 成员可见，返回最近 60 条版本（时间、版本号、精度）；`POST /api/docs/:id/versions/:versionId/restore` 仅 owner / editor，返回该版本的快照内容，并校验版本归属该文档的 Y.Doc，避免跨文档读取。

**恢复机制（关键取舍）**：不采用“服务端把历史快照二进制写回 Y.Doc”的做法——Yjs 的状态更新只能表达新增，无法表达“删除历史内容后重新插入”，直接合并会让恢复失效。M2 改为由持有协同连接的可写客户端把快照内容写回当前文档，删除与插入都成为正常协同事务：

- **文档**：把快照还原到临时 Y.Doc，用临时协同编辑器转换为 ProseMirror JSON，再 `setContent` 写回当前编辑器；在线成员无需重连即可收敛。
- **表格**：bridge 按 opLog 长度增量消费，无法处理“历史 op 被删除”，因此把快照中的 opLog 整体替换进当前 Y.Doc，再通过 stateless 控制消息通知同文档所有客户端重载重建 Univer；协同分片只转发这一种控制消息。

**实测（真实 Edge + 本地双分片）**：

| 场景 | 结果 |
|---|---|
| 表格：快照后改为 V2，恢复首版 | 恢复端与旁观端 A1 均回到 V1，双端重载后协同一致 |
| 文档：快照后追加第二版，恢复首版 | 恢复端与旁观端正文均只剩首版内容，无重连、无手工刷新 |
| 版本列表精度 | 7 天内版本标注“内容级” |

已知边界：版本列表只展示最近 60 条；恢复沿用当前编辑器约束（单文档 8 万字上限）；只读成员不可恢复。

### 9.7 结论

M0 三项红线与 M1 四项性能门全部通过：单 sheet 200 人协同 40/40 op 无丢失、8 万字文档满负载打开 parse 35–36ms、真实 vsync 设备编辑区 0 慢帧、spectator 出站带宽亚线性增长。M1 范围内的账号密码登录、最小 ACL、自动保存状态、8 万字上限拦截均已在提交 `0521b19` 中落地并验证。SSO 按约定推迟到后续里程碑。

---

**一句话收束**：这份设计的核心不是“把飞书的能力搬过来”，而是**在 200 人单文档这条红线上，用小团队能运维、AI 能安全生成、故障边界可接受的方式，把 Yjs + Hocuspocus + Univer OSS 的组合推到它能稳定工作的上限**。M0 的 3 周红线验证是整个计划的成败点——如果 200 人 awareness 治理没有在那里跑通，后面所有里程碑的乐观排期都不成立。
